# TraceLab Dataset Analysis

## 1. Overview

This document describes the exploration, profiling, and validation of the TraceLab dataset used in the coding-agent storage I/O research project.

The primary objective is to understand how coding agents interact with tools, how their execution activity can be reconstructed from available traces, and how these traces can support the characterization and prediction of storage I/O workloads.

The analysis focuses on:

- Understanding the TraceLab dataset structure.
- Exploring available tables and their relationships.
- Characterizing sessions, projects, models, rounds, and tool calls.
- Identifying timing and execution information.
- Investigating tool-call and tool-result relationships.
- Identifying missing information required for storage I/O modeling.
- Establishing a foundation for reproducible workload generation and performance experiments.

**Dataset:** `syfi_coding_trace.duckdb`

**Database location:**

```text
datasets/raw/syfi_coding_trace.duckdb
```
---

## 2. Research Context

The research investigates storage I/O behavior in concurrent coding-agent workloads.

Coding agents interact with files, repositories, terminals, and other tools while executing tasks. Their execution generates different types of artifacts, including:

- Session state.
- Conversation history.
- Tool-call information.
- Tool execution results.
- Intermediate files.
- Project-related data.
- Retrieval and context information.

These activities can generate storage operations such as reads, writes, metadata operations, and synchronization.

However, application-level execution traces do not necessarily contain the actual block-level storage operations generated by the underlying system.

Therefore, TraceLab is being investigated as a potential source for understanding coding-agent behavior and constructing representative workloads for subsequent storage experiments.

## 3. Dataset Exploration

### 3.1 Database Structure

The DuckDB database contains four main tables:

| Table | Description |
|---|---|
| `rounds` | Contains information about execution rounds and their associated context. |
| `tool_calls` | Contains tool-call information associated with coding-agent execution. |
| `timing_events` | Contains timing and event information associated with execution activity. |
| `trace_source` | Contains trace-source information. |

These tables provide different perspectives on coding-agent execution.

The analysis focuses particularly on understanding how information from `rounds`, `tool_calls`, and `timing_events` can be connected.

### 3.2 Schema Inspection

The database schema was inspected using DuckDB.

The observed schema contains:

| Table | Number of columns |
|---|---:|
| `rounds` | 27 |
| `tool_calls` | 18 |
| `timing_events` | 11 |
| `trace_source` | 1 |

The schema includes different data types, including:

- `UUID`
- `TIMESTAMP`
- `BOOLEAN`
- `HUGEINT`
- `VARCHAR`
- `VARCHAR[]`

All displayed columns were reported as nullable, and no declared primary keys, foreign keys, or default values were identified during schema inspection.

This means relationships between tables must be investigated using the available identifiers and observed data rather than assuming enforced database constraints.

### 3.3 Important Considerations

The presence of identifiers in multiple tables does not automatically guarantee a valid relationship.

For example:

- A tool-call ID may appear in multiple event records.
- A tool-result event may not have a corresponding call in the same round.
- A globally matching identifier may not establish a same-round relationship.
- Some relationships may require additional session, project, or round context.

These considerations are important when reconstructing execution sequences.

## 5. Tool-Call Coverage Analysis

Tool-call coverage was included in the initial profiling to understand how much of the coding-agent execution activity can be reconstructed from available tool-call information.

The profiling script examines:

- Total tool calls.
- Unique tool names.
- Calls with command skeletons.
- Calls with extracted execution information.

The purpose is to understand how much information is available for reconstructing the operations performed by coding agents.

### 5.1 Research Relevance

Tool-call information can help identify activities such as:

- File operations.
- Terminal commands.
- Repository interactions.
- Search operations.
- Other tool-mediated execution.

These activities may be useful for constructing representative workload patterns.

However, the presence of a tool call does not directly reveal the actual storage operations performed by the operating system or storage device.

For example, a command that reads a file may result in different physical I/O behavior depending on filesystem caching, application buffering, and the underlying storage system.

Therefore, tool-call information should be treated as application-level execution evidence rather than direct storage I/O measurements.

## 6. Tool-Call and Tool-Result Relationship Analysis

An important part of the dataset investigation is determining whether tool calls can be reliably connected to their corresponding tool-result events.

This is necessary for reconstructing execution sequences and identifying the duration and outcome of tool-mediated operations.

### 6.1 Validation Script

The relationship validation was implemented and executed using:

```powershell
python scripts/validate_tool_call_relationships.py
```

The script evaluates:

1. Total timing events.
2. Events containing non-null tool IDs.
3. Events containing non-empty tool IDs.
4. Distinct tool-call IDs.
5. Global tool-call matching.
6. Composite matching.
7. Composite-unmatched events.
8. Events that match globally but not within the same round.

### 6.2 Matching Approaches

**Global matching**

Global matching checks whether an event's tool-call ID exists in the global collection of tool-call identifiers.

This establishes whether the identifier has a corresponding record somewhere in the available dataset.

**Composite matching**

Composite matching applies additional execution context when checking relationships, including round-level context.

This provides a stricter validation than checking identifiers globally.

The distinction is important because a globally matching identifier does not necessarily establish that the call and result belong to the same execution round.

The difference between global matches and composite matches is:

```text

```

The reported composite-unmatched count is 542,286.

There is therefore a difference of 33 events between the composite-unmatched count and the globally-matched-but-not-in-the-same-round count.

This difference should be reconciled by inspecting the validation logic and the underlying event records rather than assuming that both categories are perfectly equivalent.

### 7.6 Initial Interpretation

The current results establish that tool-result relationships cannot always be reconstructed through same-round matching.

Possible explanations that require investigation include:

1. Tool calls and results may be represented across different rounds.
2. Some tool-result records may use a different relationship structure.
3. Some calls may be missing from the extracted tool-call records.
4. The composite matching criteria may be stricter than the actual relationship structure in the dataset.
5. Duplicate or repeated identifiers may influence matching counts.

These are hypotheses, not confirmed explanations.

The current validation should therefore be considered an initial relationship audit rather than proof of missing or corrupted records.

## 8. Implications for Storage I/O Research

The relationship-validation results are important because the research requires reliable reconstruction of coding-agent execution activity.

If tool calls and results cannot be reliably connected, it becomes difficult to establish:

- The complete execution sequence.
- Tool execution boundaries.
- Operation durations.
- Relationships between commands and their results.
- The number of operations associated with a session.
- The timing and ordering of application-level activities.

These limitations may affect subsequent workload generation.

### 8.1 Application-Level Events vs. Physical Storage I/O

A central distinction in this research is that application-level events are not equivalent to physical storage I/O.

For example:

| Application activity | Potential storage activity |
|---|---|
| Reading a source file | Filesystem read |
| Writing generated code | Filesystem write |
| Updating session state | Small or large metadata/data writes |
| Restoring a session | Reads of previously stored artifacts |
| Updating retrieval data | Reads and writes associated with retrieval storage |
| Running terminal commands | Potential filesystem and metadata operations |

These are potential relationships, not directly measured I/O operations.

Actual storage behavior depends on several factors:

- Filesystem caching.
- Page cache.
- Application buffering.
- Writeback behavior.
- Filesystem metadata.
- Storage-device characteristics.
- Concurrent workloads.

Therefore, application-level traces need to be combined with system-level instrumentation and controlled experiments before drawing conclusions about actual storage performance.

## 9. Data Limitations and Open Questions

The initial exploration identified several areas requiring additional investigation.

### 9.1 Tool-Call Relationship Completeness

The latest validation identified 542,286 composite-unmatched events.

Their relationships need to be investigated before they can be used reliably for workload reconstruction.

### 9.2 Missing System-Level I/O Measurements

The dataset provides application-level execution information, but this does not automatically provide:

- Block-device read/write operations.
- Actual bytes transferred.
- IOPS.
- Storage latency.
- Queue depth.
- Filesystem-level operation counts.
- Device utilization.

These measurements will need to be collected during controlled workload execution.

### 9.3 Session Artifact Identification

Further investigation is needed to determine how session-related artifacts can be identified and connected to execution activity.

Relevant artifact categories include:

- Session state.
- Conversation history.
- Intermediate execution data.
- Tool-result data.
- Retrieval-related data.
- Project files.

### 9.4 Concurrent Workload Representation

The dataset contains many sessions, but the existence of multiple sessions does not establish that they executed concurrently.

Concurrency must be characterized using reliable timing information or reproduced through controlled workload experiments.

### 9.5 Model and Tool Variability

Different models and tools may generate different execution patterns.

The impact of these differences on storage workload characteristics remains to be investigated.

## 13. Conclusion

The initial TraceLab investigation demonstrates that the dataset provides substantial application-level execution information for studying coding-agent workloads.

The database contains 665,453 rounds, 8,058 unique sessions, 356 unique projects, and 30 unique models.

The latest tool-call relationship validation identified 2,688,829 timing events, of which 1,487,041 contain non-null and non-empty tool IDs.

Global matching identified 1,487,008 matched events, while composite matching identified 944,755 matched events. A total of 542,286 events remained unmatched under composite validation, all of which were classified as tool-result events originating from `user.content.tool_result`.

These results highlight the importance of understanding the relationship between tool calls, tool results, and execution rounds before using the traces to construct representative workloads.

The next priority is to investigate unmatched tool-result relationships and establish a reliable trace-to-workload mapping.

Ultimately, the goal is to connect coding-agent execution behavior with measured storage I/O characteristics, develop session-level workload prediction, and evaluate storage saturation under concurrent agent workloads.

**Current status:** Initial dataset exploration and relationship validation completed. Detailed relationship investigation and session-level workload characterization are the next priorities.
